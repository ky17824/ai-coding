# AI GTM 어시스턴트 질문 중복 방지 개선안

## 결론

현재 문제는 모델 성능보다 질문 상태 관리 방식에 있습니다. AI가 매 호출마다 다음 질문을 새로 만들고, 서버는 최근 8개 메시지만 전달하며, 반환된 `questionKey`도 저장하지 않습니다. 따라서 오래된 답변을 잊고 같은 주제의 표현만 바꾼 질문을 반복합니다.

개선 방향은 **AI가 질문 순서를 결정하지 않도록 하고, 서버가 정해진 정보 항목 중 부족한 항목 하나만 선택**하는 것입니다. AI는 필요한 정보가 모인 뒤 실행 계획을 작성하는 역할에 집중합니다.

## 확인된 원인

1. **질문 이력이 최근 8개 메시지로 잘림**
   `app/api/gtm-assistant/turn/route.ts:226-230, 348-355`에서 대화를 `.slice(-8)`로 저장합니다. 이전에 답한 수량·가격·예산 정보가 밀려나면 모델은 이를 알 수 없습니다.

2. **질문의 고유 식별자를 버림**
   모델 응답에는 `questionKey`가 있지만(`lib/gtm-assistant.ts:39-47`), 저장할 때는 질문 문장만 남깁니다(`app/api/gtm-assistant/turn/route.ts:348-355`). 서버가 “이미 물은 항목”을 판별할 수 없습니다.

3. **질문 수가 실제 누적 질문 수가 아님**
   `questionCount`를 최근 메시지에서 다시 계산합니다(`app/api/gtm-assistant/turn/route.ts:298-300`). 최근 8개만 남기므로 “총 7개 이내”라는 프롬프트 제한이 사실상 초기화됩니다.

4. **20회 제한이 답변 처리보다 먼저 실행됨**
   기존 계획의 `turn_count`가 20이면 사용자의 새 답변을 저장하기 전에 429를 반환합니다(`app/api/gtm-assistant/turn/route.ts:251-252`). 화면에는 기존 질문이 남아 있어 멈춘 것처럼 보입니다.

5. **프롬프트만으로 중복을 막으려 함**
   “한 번에 한 질문, 총 7개”는 지시문일 뿐 코드로 강제되지 않습니다(`app/api/gtm-assistant/turn/route.ts:317-318`).

## 최소 개선 설계

### 1. 질문을 고정된 정보 항목으로 관리

새 테이블이나 외부 라이브러리는 만들지 않습니다. 현재 `founder_context`와 `recent_messages`를 재사용하고, 질문 항목만 코드에 고정합니다.

우선 확인 항목:

- `offeringName`: 글로벌 론칭 제품·서비스·솔루션명
- `offeringSummary`: 무엇을 제공하는지
- `customerProblem`: 해결하려는 고객 문제
- `coreValue`: 선택받을 핵심 가치
- `targetCountry`: 초기 목표국가
- `targetCustomer`: 초기 목표고객
- `resources`: 인력·재고·예산 등 가용 자원
- `deadline`: 목표 기한
- `constraints`: 규제·비용·운영 제약

각 항목은 `missing`, `answered`, `unknown_confirmed` 중 하나로 판정합니다.

- 빈 값이면 `missing`
- 구체적인 답이면 `answered`
- “모름”, “확인 필요”, “아직 없음”이면 `unknown_confirmed`

`unknown_confirmed`는 다시 묻지 않고 계획의 가정 또는 확인 과제로 전환합니다.

### 2. 다음 질문은 서버가 결정

처리 순서:

1. 현재 답변을 직전 `questionKey`에 저장
2. 이미 `answered` 또는 `unknown_confirmed`인 항목 제외
3. 우선순위가 가장 높은 `missing` 항목 하나만 선택
4. 해당 항목을 아직 묻지 않았을 때만 질문
5. 부족한 답이면 같은 항목에 한 번만 보충 질문
6. 그래도 부족하거나 “확인 필요”이면 실행 과제로 바꾸고 계획 생성

AI는 질문 선택에 관여하지 않고, 모든 항목이 처리된 뒤 계획 초안만 생성합니다.

### 3. 질문 저장 형식 보강

`recent_messages`에 문장만 저장하지 않고 다음처럼 구조화합니다.

```json
{
  "role": "assistant",
  "questionKey": "validationBudget",
  "content": "30일 고객 검증에 사용할 수 있는 최대 예산은 얼마인가요?",
  "status": "asked"
}
```

사용자 답변도 같은 `questionKey`와 함께 저장합니다. 질문은 최대 3개 보충 질문만 허용하므로 전체 이력을 보관해도 크기가 작고 `.slice(-8)`이 필요 없습니다.

### 4. 부분 답변은 부족한 값만 질문

예: 사용자가 “판매가는 40 SGD이고 원가는 아직 모릅니다”라고 답한 경우:

- 목표 판매가: `answered = 40 SGD`
- 단위원가: `unknown_confirmed`
- 판매가를 다시 묻지 않음
- 단위원가는 “7일 이내 제조·배송 포함 원가 확인” 과제로 계획에 포함

예: “제품 100개가 있다”고 이미 답했다면 재고 수량은 다시 묻지 않습니다. 예산이 별도 필요하면 “재고 100개는 확인했습니다. 추가 검증비의 상한만 알려주세요”처럼 이미 확인된 값을 명시하고 부족한 값 하나만 묻습니다.

### 5. 종료 조건을 코드로 강제

- 항목당 보충 질문 최대 1회
- 전체 보충 질문 최대 3회
- `unknown_confirmed`도 완료된 응답으로 계산
- 한도 도달 시 429가 아니라 현재 정보와 명시된 가정으로 계획 생성
- 기존 `turn_count=20` 계획도 차단하지 않고 새 상태 규칙으로 복구
- 계획 생성 실패 시 기존 결정론적 기본 계획을 반환

## 화면 개선

질문 카드 상단에 다음만 표시합니다.

- `필수 정보 7/9 완료`
- `추가 확인 1/3`
- 질문이 필요한 이유 한 줄

입력 아래에는 `확인 필요` 버튼을 둡니다. 이를 선택하면 같은 내용을 반복 질문하지 않고 확인 과제로 넘깁니다.

오류 시 기존 질문을 그대로 무한 재시도하게 두지 않고, 오류 문구와 `현재 정보로 계획 만들기` 버튼을 표시합니다.

## 구현 순서

1. `lib/gtm-assistant.ts`에 고정 정보 항목, 답변 상태 판정, 다음 부족 항목 선택 함수를 추가합니다.
2. `app/api/gtm-assistant/turn/route.ts`에서 모델의 `next_question` 생성을 제거하고 서버 선택 질문을 먼저 반환합니다.
3. 같은 라우트에서 `questionKey`가 포함된 전체 짧은 문답 이력을 저장하고 `.slice(-8)` 및 최근 메시지 기반 질문 수 계산을 제거합니다.
4. `turn_count >= 20`의 429 차단을 없애고, 질문 한도 도달 시 계획 생성으로 전환합니다.
5. `components/gtm-assistant.tsx`에서 저장된 `questionKey`를 복원하고 완료 수·질문 수·`확인 필요`·오류 대체 버튼을 표시합니다.
6. `lib/gtm-assistant.test.ts`에 아래 회귀 검증을 추가합니다.

## 완료 기준

- 이미 `answered`인 `questionKey`는 다시 반환되지 않는다.
- “확인 필요”로 답한 항목은 다시 묻지 않고 계획의 가정 또는 확인 과제가 된다.
- 복합 답변에서는 이미 답한 값이 아니라 부족한 값 하나만 질문한다.
- 최근 대화 길이와 관계없이 누적 질문 수가 유지된다.
- 전체 추가 질문은 3개를 넘지 않는다.
- 질문 한도나 기존 `turn_count=20` 때문에 429로 멈추지 않고 계획을 생성한다.
- API 재시도 시 동일 질문을 새 질문으로 중복 저장하지 않는다.
- 현재 사례의 `제품 100개`, `판매가 40 SGD`, `원가 확인 필요`가 각각 보존되고 같은 내용이 재질문되지 않는다.

## 제외한 사항

- 별도 질문 관리 테이블: 현재 규모에서는 불필요합니다. 감사·분석 요구가 생길 때 추가합니다.
- AI 기반 답변 충분성 재판정: 다시 불확실성을 만들 수 있어 제외합니다. 우선은 빈 값과 명시적 미확인 표현만 코드로 판정합니다.
- 질문 문구 자유 생성: 중복 원인이므로 제거하고 고정 문구를 사용합니다.
