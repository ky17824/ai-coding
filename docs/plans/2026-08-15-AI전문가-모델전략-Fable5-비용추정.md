## 3. max_tokens · 스트리밍 (Critic C1 반영 — v2의 값은 자체 가정보다 작아 폐기)

**원칙: max_tokens ≥ (가시 출력 + 사고) high 가정 × 1.3 여유.** Fable 5·Opus 5 모두 사고 토큰이 max_tokens를 공유하므로, 작게 잡으면 절단 → questionCoverage 완전일치 계약(`ai-agent-report.ts:181-184`)이 throw → **주문 실패**가 됩니다.

| 콜 | high 가정(가시+사고) | **권장 max_tokens** | Opus 5 최악 비용 | Fable 5 최악 비용 |
|---|---|---|---|---|
| 1단계 | 3,500 | **8,000** | $0.04 (Haiku) | — |
| 2단계 개별 (medium) | 16,000 | **24,000** | $0.60 | $1.20 |
| 2단계 패키지 (high) | 24,000 | **32,000** | $0.80 | $1.60 |
| 3단계 개별 (medium) | 29,000 | **40,000** | $1.00 | $2.00 |
| 3단계 패키지 (high) | 57,000 | **64,000** | $1.60 | $3.20 |

- **G9(사전 검사)**: max_tokens 미설정 콜은 발사 자체 금지. 미설정 Fable 5 콜은 단일 콜 128K = **$6.40**까지 가능하며, 이는 ₩149,000 이상 상품의 비율 상한($7.02~)을 통과해 버리므로 **G9가 실질 방어선**입니다(G8 상한은 고가 상품에서 폭주 콜을 못 막음).
- **스트리밍**: 서버에서 스트리밍으로 받아 누적 후 기존 응답 형태로 반환하면 클라이언트 변경 불필요. 장시간 요청에 SDK가 스트리밍을 요구하는지는 **미확인**(대형 max_tokens 논스트리밍은 SDK 타임아웃 위험이 알려져 있어 스트리밍 권장).

## 4. 지연 예산 — 동기 300초 상한 (실측 선행 필수)

**전제**: 현행은 동기 단일 POST, `vercel.json` maxDuration 미설정(실제 적용값 **미확인**). 처리 속도(tok/s)도 **미확인**.

| 구간 | 예산 | base 출력(가시+사고) | 필요 처리 속도 |
|---|---|---|---|
| 1단계 (Haiku) | ≤ 15초 | 2,000 | 133 tok/s |
| 2단계 (Opus, 검색 8회 왕복 40~90초 포함) | ≤ 120초 | 10,500 | **131~350 tok/s** |
| 3단계 개별 | ≤ 150초 | 19,000 | **127 tok/s** |
| 3단계 패키지 7종 | ≤ 150초 | 45,000 | **300 tok/s — 비현실적** |

**결론**:
- 개별 상품은 300초 안에 들어올 가능성이 있으나 여유가 없습니다.
- **패키지(특히 7종)는 현행 구조에서도 이미 300초 초과가 유력합니다.** 이는 모델 이관과 무관한 기존 문제이며 이관보다 우선합니다.
- 300초 초과로 함수가 강제 종료되면 catch가 실행되지 않아 run이 **15분 lease 만료까지 `generating` 고착** 후 stale retry로 회수됩니다(`migrations/010:167`) — 사용자 체감은 "15분 멈춤 후 재시도". (Critic C8)
- **Step 0(현행 p50/p99 실측)이 차단 과제**입니다. 초과 확인 시 잡 큐 도입(최소 구현: `ai_agent_runs` 상태 + 클라이언트 폴링, Supabase만으로 가능)을 별도 선행 과제로 분리합니다.

## 5. 품질 로직 — "이미 구현된 것"과 "신규"의 구분 (Critic C2 반영)

> v2 계획이 "신규 도입"으로 제안했던 인용 화이트리스트·공식 도메인 게이트·TAM/SAM/SOM 검증은 **전부 이미 프로덕션에 구현되어 있습니다**(§1 참조). 이 절은 실제로 새로운 것만 남깁니다.

### 5.1 기존 하드 게이트 — **현행 유지 (완화하지 않음)**

현행은 인용 위반·산술 위반 시 **생성 실패(throw)** 입니다. v2가 제안한 "위반 finding을 human_verification으로 강등 후 납품"은 보증 수준을 낮추는 제품 의사결정이며, 특히 규제 상품(₩249,000)에서 근거 없는 결론이 딱지만 붙어 출고될 위험이 있습니다. **기본 결정: 현행 하드 실패 유지.** 강등 방식은 실측(§10)에서 실패율이 높게 나올 경우에만, 비규제 상품 한정으로 재검토합니다.

### 5.2 신규 — 산술의 코드 이관 (모델 이관과 무관, 즉시 적용 가능)

| 항목 | 규칙 | 상태 |
|---|---|---|
| **SOM 도출** | 모델이 `{formula, inputs[]}`만 출력, 서버가 실제 연산. 모델의 최종값은 폐기 | **신규** |
| TCE 합산 | 항목 배열 합 = 총액 검증, 불일치 시 코드 합계 채택 | 구현 여부 **확인 필요** |
| 통화 환산 | 단일 상수로 서버 적용. 모델 환산값 무시 | 신규(상수 통일과 함께, §5.3) |
| TAM≥SAM≥SOM, low≤base≤high | — | **이미 구현** (`ai-agent-report.ts:218-223`) |

부수 효과: formula 방식은 모델이 곱셈을 하지 않는 만큼 사고 토큰도 줄입니다(절감폭 미확인).

### 5.3 신규 — 환율 상수 통일 (Critic C5)

코드에 **1,500 하드코딩**(`ai-agent-report.ts:169`, 원가 KRW 기록)과 플랫폼 규칙 **1,400**(USD 표시가 산정)이 공존합니다. G8 상한(÷1,400)과 원가 기록(×1,500)이 다른 환율을 쓰면 판정이 어긋납니다. **결정: 공유 상수 `USD_KRW = 1400`으로 통일**(플랫폼 확정 규칙). 기존 1,500 기록은 원가를 7% 과대 기록해 왔음을 갱신 시점에 기록합니다. (보수 버퍼로 1,500 유지를 원하시면 상한식도 1,500으로 통일 — 어느 쪽이든 **하나로**.)

### 5.4 신규 — 단일 콜 내부 모순 처리

현행 패키지는 단일 합성 콜이므로 "N개 보고서 조정 패스"는 불필요합니다. 기존 `contradictions` 스키마 필드에 해소 우선순위만 부여합니다: ① 근거 등급 `fact` > `estimate` > `analog_assumption` ② 소관 영역 우선(규제 수치는 규제 섹션, 비용은 TCE) ③ **미해소는 은폐하지 않고 "견해 차이"로 노출** + `human_verification`.

## 6. 자동 품질 게이트 (임계값은 초기 가정 — shadow 실측 후 조정)

| ID | 게이트 | 판정 | 실패 시 조치 | 상태 |
|---|---|---|---|---|
| G1 | 스키마 파싱 (`output_config.format` json_schema) | Hard | 재시도 1회 → 폴백 모델 → 주문 홀드 | 확정 |
| G2 | 인용 화이트리스트 (기존 구현 유지) | Hard | **현행대로 생성 실패** → 동일 요청 내 재시도 1회 | 기존 구현 |
| G3 | questionCoverage 완전일치 | Hard | 누락 목록 명시 후 3단계만 재생성 1회 | 기존 계약 |
| G4 | 산술 재계산 일치 (SOM formula·TCE 합산) | Hard | 코드값 채택 + 로그, 불일치 3건↑ 시 재생성 (**3건은 가정**) | 신규 |
| G5 | 규제 상품 공식 도메인 인용 ≥1건 | Hard | 2단계부터 재실행 | 기존 구현 |
| G6 | `stop_reason != "refusal"` | 자동 폴백 | 서버측 `fallbacks` 재라우팅, 2회 실패 시 홀드 | 신규(Anthropic 한정) |
| G7 | `findings ≥ 5`, `actionPlan ≥ 3`, `evidenceGaps` 존재 (**수치는 가정**) | Soft | 경고 + 검수 큐 | 신규 |
| G8 | `cost_usd ≤ order.amount_krw × 0.06 ÷ USD_KRW` | Hard | 즉시 중단 + 알림 | 신규 |
| G9 | **max_tokens 명시 + 스트리밍** — 사전 검사 | Hard | 미설정 콜 발사 금지 | 신규, **실질 방어선** |

- **재시도는 `generation_count`를 소모하지 않습니다** — 동일 HTTP 요청 내 재시도는 `reserve` 재호출이 없어 자동 충족(별도 마이그레이션 불필요, Critic C8 확인). Hard 게이트당 재시도 1회 상한.
- **G8의 한계(정직 고지)**: 비용은 콜 종료 후에만 산출되므로(`route.ts:319`) "즉시 중단"은 콜 사이에서만 가능하고, ₩199,000 이상 상품은 상한이 커서 단일 폭주 콜을 못 막습니다. 폭주 방지는 G9가 담당합니다. "부분 결과 보존"은 현행 단일 jsonb 저장 구조에 경로가 없어 **하지 않습니다**.

### 7.7 프롬프트 캐시·Batch

- 캐시는 **model-scoped**. 채택안은 Opus 5 풀에 2콜(2·3단계)뿐 → **1시간 TTL(쓰기 2×)은 손익분기 3콜 미달로 손해, 5분 TTL(1.25×)만 실익**: 공통 프리픽스 10,000토큰 가정 시 절감 $0.0325/실행(~3%). 2·3단계가 순차 실행이라 5분 내 조건 충족.
  - ⚠️ 전제 미검증: 2·3단계의 instructions·입력이 달라 "공통 프리픽스 10K"가 실재하는지 **미확인**(§11 검증 항목). 1단계 Haiku는 풀에 1콜 + 최소 4,096토큰 경계라 캐시 미적용.
  - v1 혼합 4모델 안 기각 근거: 풀 4분할로 절감 반토막($1.16→$0.59), 병렬 동시 발사와 결합 시 전원 miss + 2× write로 **+$0.87 손해 반전**.
- **Batch API(토큰 50% 할인)**: 동기 POST 구조상 적용 불가. 잡 큐 도입 후에만 검토. `fallbacks` 미지원(G6 앱 레벨 재구현 필요), 최대 24시간 지연.

### 7.8 비용 추적 인프라 매핑 + 필수 리팩터 (Critic C7)

- `p_model_cost_usd` / `p_tool_cost_usd`(웹서치 × $0.01) / `web_search_calls`(`server_tool_use.web_search_requests`, 필드 경로 **미확인**) — **기존 3개 컬럼으로 충분. 스키마 변경 불필요.**
- 단, 현행은 3콜 usage를 `addUsage`로 **합산 후** 단일 단가 함수(`calculateSolCostUsd`)로 계산합니다. **콜별 모델이 다르면 합산 usage로는 원가 계산이 불가** → (i) usage를 콜 단위로 분리 유지 (ii) 모델별 단가 테이블 도입 (iii) 콜 단위 계산 후 합산 — 3개 항목의 리팩터가 이관의 선행 작업입니다.
- 검증용으로 **`usage_raw jsonb` 컬럼 1개만 추가**해 초기 100회 실행의 3콜 원본 usage를 덤프. 분해 테이블은 미리 만들지 않습니다.
- 사고 토큰이 `output_tokens`에 합산 보고되는지 **미확인** — 합산이라면 산식 변경 불필요(§10 최우선 검증).

```
                        │
                        v
                 Step 5 Fable 5 shadow 60건 ($76.20) → 승격/종료 판단 (별도 ADR)
```

| Step | 수용 기준 |
