## 1. 전제 확인 (실측)

- 문항 **55개**, 배점 합계 **정확히 100.0**
- 게이트 차단(`critical: true`) 문항 **7개**: Q5 총진입비용, Q8 전담 책임자, Q10 유료 판매 경험, Q19 법적 분류, Q29 현지 작동 시험, Q43 손익 책임자, Q47 긴급 전달 경로 → **전부 유지 대상**

## 2. 제거 원칙

1. ★(게이트 차단) 문항은 건드리지 않는다
2. 짝이 되는 중복 중 **더 구체적이고 늦은 단계의 문항을 남긴다** (실행에 가까운 쪽이 판별력이 높다)
3. 아이템(12개 영역)당 최소 3문항은 남긴다 — 영역 점수가 문항 1~2개에 좌우되면 노이즈가 커진다
4. 경험 유무를 묻는 문항보다 **체계 보유를 묻는 문항**을 남긴다 (운이 아니라 준비도를 재는 것이므로)

## 4. 제거 방식 — 삭제하지 말고 은퇴(retire)시킨다

물리 삭제하면 프로덕션 `action_items` 34행 중 제거 대상 id를 참조하는 행이 고아가 되어, **i18n 계획에서 "0건이라 안 고쳐도 된다"고 봉인한 폴백 결함 B가 그대로 되살아납니다** (`docs/survey/VERSIONS.md`의 경고가 바로 이 상황).

```ts
// lib/intake-questions.ts — 제거 대상 10개에만 추가
retired: true
```

- **진단 폼**: `retired` 문항을 제외하고 렌더 → 응답자는 45개만 봄
- **채점**: active 문항만 합산 (기존 동적 합산이 그대로 동작)
- **과거 데이터 표시**: 대시보드·어시스턴트·관리자 화면의 액션 재도출은 전체 카탈로그(은퇴 포함)에서 조회 → 고아 0 유지
- **API 검증**: `max(55)` → active 개수 기준으로 (`ACTIVE_QUESTION_COUNT` 파생 상수)

이 방식이면 마이그레이션도, 과거 응답 데이터 변환도 필요 없습니다.

| preparing | 40 | 36.0 | 〃 |
| ready | 30 | 25.5 | 〃 |
| 합계 | 100 | 86.5 | **스테이지 30/40/30 복원은 하지 않음** — 게이트는 `totalScore × 0.8` 상대 비율이라 절대값 무관. 화면 표시 점수도 `(positive/total)×100`이라 무관 |
