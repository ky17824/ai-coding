## 0. 먼저 알아두실 것 — 카드 결제는 이미 만들어져 있습니다

"어떻게 신용카드 결제를 할 수 있을까"가 질문이셨는데, **코드는 이미 대부분 존재합니다.** 새로 만들 게 아니라 **켜는 것**이 과제입니다.

|---|---|---|
| PortOne SDK (브라우저·서버) | ✅ 설치됨 | `package.json:14-15` |
| 결제창 호출 | ✅ | `components/checkout-button.tsx` |

| 결제 상태 정합성 처리 | ✅ | `lib/payments.ts` — 중복 무시, 금액 불일치 시 `disputed` |

**빠진 것은 세 가지입니다.**

1. **환경변수 4개가 전부 미설정** → 지금은 결제가 아예 동작하지 않습니다

3. **세금 처리·정산 주기·분쟁 절차**가 코드에도 문서에도 없음

## 1. 실제 카드 결제를 받기까지 — 코드 vs 행정

### 코드 (사람이 하루면 끝나는 일)

| # | 작업 | 완료 기준 |
|---|---|---|
| C1 | Vercel 환경변수 4개 등록 | 프로덕션에서 결제창이 뜬다 |
| C2 | PortOne 콘솔에 웹훅 URL 등록 (`https://global-gtm.vercel.app/api/portone/webhook`) | 테스트 결제 1건이 `orders.status = paid` 로 전이 |
| C3 | 테스트 결제 → 환불 왕복 1회 | `refunded` 전이 + PortOne 콘솔에 취소 기록 |

**C1~C3은 코드 수정이 필요 없습니다.** 설정만 하면 동작하도록 이미 만들어져 있습니다.

### 행정 (몇 주 걸리는 일, 병렬 진행)

| # | 항목 | 비고 |
|---|---|---|
| A1 | 사업자등록증 | 이미 있으시면 생략 |
| A2 | ⚖️ **통신판매업 신고** — 중개 구조이므로 **통신판매중개업**에 해당하는지 확인 | 관할 구청. 중개자 고지 의무가 따라붙음 |
| A3 | PortOne 가입 + **PG사 심사** | 카드사 등록까지 통상 1~3주. 업종·매출 규모에 따라 보증보험 요구 가능 |
| A4 | ⚖️ 정산 대금 보유 구조 검토 | 아래 2장·4장 참조 |
| A5 | 이용약관·환불정책 실물 확정 | 현재 `app/legal/*` 는 초안 상태 |

**A3이 임계 경로입니다.** 코드가 준비돼 있어도 PG 심사가 끝나기 전에는 실결제를 받을 수 없습니다.

## 2. 정산 지급 — 가장 큰 미구현 영역

전문가에게 돈을 보내는 방법 세 가지입니다. **이건 코드 문제가 아니라 사업 구조 결정입니다.**

### 가. 수동 이체 (권장 — 시작 단계)

정산 대상을 관리자 화면에서 확인하고 은행 이체로 지급, `settlements.status`를 `paid`로 갱신.

- **필요 코드**: 관리자 정산 목록 + 지급 완료 처리 버튼 (소규모)
- **장점**: 즉시 시작 가능. 거래 건수가 적을 때 자동화 비용이 아깝다
- **단점**: 건수가 늘면 사람이 감당 못 함. 이체 실수 위험
- **적정 구간**: 월 정산 건수 30건 이하

### 나. PortOne 파트너정산 연동

PortOne이 제공하는 파트너 정산 자동화를 사용.

- **필요 코드**: 전문가 계좌 등록·검증, 정산 요청 API 호출, `portone_transfer_id` 기록
- **⚠️ 확인 필요**: 이용 조건·수수료·별도 계약 여부를 **PortOne에 직접 문의해야 합니다.** 제가 확인하지 못했습니다
- **적정 구간**: 월 수십~수백 건

### 다. 전문가를 개별 판매자로 (에스크로형)

각 전문가가 자기 PG 상점을 갖고, 플랫폼은 중개만.

- **장점**: 플랫폼이 대금을 보유하지 않아 규제 부담이 가장 가벼움
- **단점**: 전문가마다 PG 가입 요구 → 온보딩 마찰이 매우 큼. 초기에는 비현실적

**권장: 가 → 나.** 지금 필요한 건 자동 송금이 아니라 **"정산 대상이 화면에 보이고, 지급 완료를 기록할 수 있는 것"**입니다. 현재는 그것조차 없습니다.

## 3. 과금 모델

### 3-1. 세 가지 선택지

| 모델 | 구조 | 장점 | 단점 |
|---|---|---|---|
| **가. 건당 중개수수료만** | 거래액의 N%를 공제 | 사용자 진입장벽 0. 지금 코드 구조와 일치 | 거래가 없으면 매출도 0. AI 비용을 회수 못 함 |
| 나. 구독만 | 월정액 | 예측 가능한 매출 | 아직 거래 실적이 없어 구독 가치를 증명하기 어려움 |
| **다. 혼합** | 무료 진단 + 유료 AI + 거래 수수료 | AI 비용을 쓰는 사람이 부담 | 가격 구조가 복잡해짐 |

**권장: 가로 시작 → 다로 확장.** 초기에는 거래를 만드는 게 최우선이고, 진입장벽을 세우면 안 됩니다.

### 3-2. AI 비용을 어디서 회수할 것인가

현재 AI 사용에 **횟수 제한만** 걸려 있고 과금은 없습니다.

- 시장·경쟁 사전조사: 3회 한도 (`app/api/gtm-assistant/research/route.ts:92`)
- 계획 생성: `generation_count` 로 집계 중

**단계적 방안:**

1. **지금** — 무료 유지. 한도가 이미 비용 상한 역할을 합니다. 실제 OpenAI 지출액을 먼저 **측정**하십시오. 측정 없이 가격을 정하면 근거가 없습니다
2. **다음** — 한도 초과분을 유료 크레딧으로 (예: 추가 조사 3회 = N원). 기존 `market_research_count` 구조를 그대로 활용 가능
3. **나중** — 전문가 서비스 구매 시 AI 무제한 같은 번들

**⚠️ 측정이 먼저입니다.** 현재 AI 1회 호출당 실제 비용을 모르는 상태에서 과금 설계를 확정하면 안 됩니다.

## 5. 영문 서비스 — USD 가격 (신규 요구사항)

### 5-1. 먼저 결정해야 할 것

**표시만 USD인지, 실제로 USD로 청구하는지**에 따라 작업량이 10배 차이 납니다.

| | 가. USD 표시 + KRW 청구 (권장) | 나. 실제 USD 청구 |
|---|---|---|
| 결제 | 기존 PortOne 그대로 | 해외결제 지원 채널 또는 별도 PG(Stripe·PayPal) 추가 계약 |
| 고객 경험 | 카드사가 환전. **명세서 금액이 표시가와 다를 수 있음** | 표시가 그대로 청구 |
| 정산 | 원화 그대로 | 외화 정산·환리스크 관리 필요 |
| 작업량 | 표시 로직만 | PG 재계약 + 코드 + 세무 |
| ⚖️ | 표시가와 청구가 차이 고지 필요 | 외화 거래 세무 처리 |

**권장: 가.** 초기 해외 거래량을 모르는 상태에서 별도 PG를 계약할 이유가 없습니다. 대신 **"실제 청구는 원화로 이루어지며 환율에 따라 금액이 달라질 수 있습니다"** 고지를 반드시 넣어야 합니다.

### 5-2. 환율 1 USD = 1,400원 적용 결과

현재 6개 서비스 가격입니다. 반올림 규칙 세 안을 함께 제시합니다.

| 서비스 | KRW | ÷1,400 | 가. $10 단위 | 나. 심리가(…9) | 다. $5 단위 |
|---|---|---|---|---|---|
| `svc-funding` | 120,000 | $85.71 | **$90** | $89 | $85 |
| `svc-unit-economics` | 180,000 | $128.57 | **$130** | $129 | $130 |
| `svc-leadership` | 240,000 | $171.43 | **$170** | $169 | $170 |
| `svc-gtm-motion` | 1,900,000 | $1,357.14 | **$1,360** | $1,359 | $1,355 |
| `svc-market-validation` | 2,200,000 | $1,571.43 | **$1,570** | $1,569 | $1,570 |
| `svc-compliance` | 2,800,000 | $2,000.00 | **$2,000** | $1,999 | $2,000 |

**권장: 가($10 단위 반올림).** 컨설팅 서비스에 `…9` 가격은 소매 느낌이 나서 어울리지 않습니다. `svc-compliance`가 정확히 $2,000으로 떨어지는 것도 우연히 깔끔합니다.

### 5-3. 구현 방식 — 환율을 코드에 박지 말 것

**하드코딩하면 환율이 바뀔 때마다 배포해야 합니다.** 두 안이 있습니다.

| | A. USD 가격을 데이터로 저장 (권장) | B. 환율 상수로 계산 |
|---|---|---|
| 방식 | `service_offerings.price_usd` 컬럼 추가. 없으면 표시 안 함 | `USD_RATE = 1400` 상수로 나눗셈 |
| 장점 | 가격을 사람이 통제. 마케팅상 원하는 숫자 지정 가능 | 컬럼 추가 불필요 |
| 단점 | 마이그레이션 1건 + 관리자 입력 UI | 환율 변동 시 코드 수정·배포. 반올림 결과가 어색해질 수 있음 |

**권장: A.** 가격은 환율 계산 결과가 아니라 **경영 판단**입니다. 1,400원은 지금 가격을 정하는 기준일 뿐, 매일 따라다닐 값이 아닙니다.

기존 `ENGLISH_SERVICE_COPY` 패턴(`lib/service-data.ts:129`)이 이미 영문 필드를 분리해 두고 있으므로, 샘플 데이터는 그 구조에 `priceUsd`를 추가하면 됩니다.

### 5-4. 완료 기준

- `/en/services` 와 `/en/services/{id}` 가 USD 표시
- 결제창 직전에 **원화 청구 고지** 노출
- `price_usd` 미설정 서비스는 USD를 표시하지 않음 (잘못된 환산가 노출 방지)
- 원화 금액과 정산 계산은 **무변경** — `orders.amount_krw` 기준 유지

## 6. 실행 순서

```
1단계  결제 켜기          C1~C3 (환경변수·웹훅·테스트 결제)   ← 코드 작업 거의 없음
       동시에 A1~A3 행정 착수 (PG 심사가 임계 경로)

2단계  정산 최소 구현      관리자 정산 목록 + 지급 완료 기록
       (2장 '가' 수동 이체)

3단계  USD 표시           price_usd 컬럼 + 영문 화면 + 원화 청구 고지

4단계  법무 확정          L1~L8, 특히 ⚖️ 항목

5단계  AI 비용 측정       실제 OpenAI 지출 집계 → 그 다음에 과금 설계
```

**1단계와 2단계 사이에 실거래를 열지 마십시오.** 정산 지급 수단 없이 결제를 받으면 전문가에게 돈을 못 주는 상태가 됩니다.

---

## 7. 리스크

| 리스크 | 대응 |
|---|---|
| PG 심사 지연으로 일정 밀림 | 1단계 행정을 지금 즉시 시작. 코드는 이미 준비됨 |
| 정산 없이 결제부터 열림 | 2단계 완료 전 실서비스 오픈 금지를 규칙으로 |
| USD 표시가와 실제 청구액 불일치 민원 | 결제 직전 고지 + 주문 내역에 원화 금액 병기 |
| 환율 급변으로 USD 가격이 부적절해짐 | `price_usd`를 데이터로 두어 배포 없이 조정 |
| AI 비용이 수수료 수입을 초과 | 5단계 측정 전까지 현행 횟수 한도 유지 |

## 8. 확인이 필요한 사항

- **PortOne 파트너정산의 조건·수수료** — 확인하지 못했습니다. PortOne에 직접 문의 필요
- **월 예상 거래 건수** — 2장의 '가/나' 선택 기준이 됩니다
- **플랫폼 수수료율** — 코드에 계산 로직은 있으나 확정된 비율을 찾지 못했습니다
- **AI 1회 호출 실비용** — 미측정
- **영문 서비스의 전문가** — USD 표시는 화면 문제이나, 영어로 상담 가능한 전문가가 실제로 있는지는 별개 문제입니다
