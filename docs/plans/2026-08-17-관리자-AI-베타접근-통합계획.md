## 0. 이 문서가 원안과 다른 점

원안의 **설계 판단은 그대로 채택한다.** `billing_mode` 도입, 실행 상태 재사용,
정확히 두 UUID, fail-closed 검증, 비용 기록 유지 — 모두 타당하다.

바뀌는 것은 **실행 순서**다. 원안 작성 이후 main이 14커밋 앞서 나갔고,
그 과정에서 원안이 전제한 마이그레이션 번호가 이미 프로덕션에 소진되었다.
이 문서는 그 충돌을 해소한 실행 계획이다.

## RALPLAN-DR 요약

### 원칙

1. **결제 게이트웨이만 우회한다.** 준비도 연동·입력·파일·추가질문·모델 호출·웹 조사·보고서·정정·비용 기록은 유료 경로와 같은 코드를 쓴다. 다른 코드를 타면 베타 테스트의 의미가 없다.
2. **권한은 서버가 판정한다.** 클라이언트가 보낸 어떤 값도 무료 여부를 결정하지 못한다.
3. **fail closed.** 플래그·UUID·역할 중 하나라도 어긋나면 유료 경로만 남는다.
4. **매출 사실을 오염시키지 않는다.** 베타 주문은 금액 0이며 매출·전환·정산·환불 지표에서 빠진다.
5. **이미 적용된 마이그레이션은 손대지 않는다.** 프로덕션에 반영된 번호를 재사용하거나 되돌리지 않는다.

### 결정 동인

1. **마이그레이션 번호 충돌** — 원안이 쓰려던 016·017이 이미 프로덕션에 적용되었다. 이 상태로 진행하면 admin user management 마이그레이션이 **조용히 건너뛰어진다.**
2. **워크트리가 main보다 14커밋 뒤처져 있다** — 미커밋 변경 19건. 다만 main과 겹치는 파일은 `app/globals.css` 하나뿐이다.
3. **0원 주문을 막는 제약이 둘 있다** — `001:146`(무명)과 `011:7-8`(명시적). 게다가 `001:145` `payment_id`는 `not null unique`라 베타 주문도 값이 필요하다.

### 검토한 선택지

**선택지 1 — 워크트리를 main에 먼저 통합하고, 번호를 다시 매긴 뒤 베타 기능을 얹는다 (채택)**
- 장점: 프로덕션 마이그레이션 이력과 어긋나지 않는다. 통합과 신규 기능이 분리되어 실패 지점이 좁다.
- 단점: 배포가 세 번으로 나뉜다.

**선택지 2 — 워크트리에서 베타 기능까지 완성한 뒤 한 번에 병합**
- 장점: 배포가 한 번이다.
- 단점: **016 충돌이 그대로 남는다.** 워크트리의 `016_admin_user_management.sql`은 원격에 016이 이미 적용되어 있어 `supabase db push`가 **건너뛴다.** 테이블이 생기지 않은 채 앱만 배포되어 런타임에 깨진다.
- 기각 사유: 동인 1을 해결하지 못한다.

**선택지 3 — 관리자에게 100% 할인 쿠폰을 발행해 기존 결제 경로를 그대로 태운다**
- 장점: 스키마 변경이 없다.
- 단점: 쿠폰 시스템이 없어 새로 만들어야 하고(원안 비범위), 0원 결제가 성립하더라도 매출·전환 지표에 0원 결제가 섞인다.
- 기각 사유: 원칙 4와 원안의 비범위를 위반한다.

**선택지 4 — 프로덕션 DB에서 관리자 주문을 수동 INSERT**
- 장점: 코드 변경 0.
- 단점: 매번 사람이 SQL을 실행해야 하고, `service_snapshot`·`readiness`·`terms_snapshot`을 손으로 맞춰야 하며, 실수 시 잘못된 계약이 실행에 고정된다. 반복 불가.
- 기각 사유: 원칙 1을 지킬 수 없다(같은 코드 경로가 아니다).

**선택지 5 — PortOne 테스트 모드 채널 키를 두 계정에만 적용**
- 장점: **원칙 1을 가장 완전히 만족한다.** 결제 게이트웨이와 webhook, `reconcile_ai_payment`까지
  전 경로를 실제로 태운다. 스키마 변경·제약 수술·`payment_id` 네임스페이스·부분 인덱스가 **전부 불필요**하다.
- 단점: ① 테스트 결제라도 **0이 아닌 금액이 프로덕션 `orders`에 남아** 원칙 4를 깬다.
  ② `NEXT_PUBLIC_PORTONE_CHANNEL_KEY`가 `checkout-button.tsx:79`의 전역 환경변수라
  사용자별 분기를 넣으려면 **살아 있는 결제 컴포넌트에 테스트 라우팅 로직**을 넣어야 한다.
  실수하면 실제 창업자에게 과금되거나 과금이 누락된다.
- 기각 사유: 단점 ②의 폭발 반경이 기본값 있는 컬럼 하나보다 크다. 원칙 4도 어긴다.
  **다만 선택지 1보다 원칙 1을 잘 만족한다는 점은 인정하고 기록한다.**

### 사전 부검 — 3개 시나리오

**시나리오 1: 016 충돌을 모른 채 배포해 admin user management가 통째로 누락된다.**
- 징후: 배포 후 `/admin/users`가 500. `supabase migration list`에 016이 이미 remote로 표시.
- 원인: Supabase는 번호로 적용 여부를 판정한다. 같은 016이 이미 있으면 **오류가 아니라 건너뛴다.**
- 대응: 통합 첫 단계에서 **파일명을 018로 바꾸고**, `supabase migration list`로 018이 `local`에만 있고 `remote`가 비어 있음을 눈으로 확인한 뒤 push한다.
- **메커니즘은 검증됨.** `supabase migration list`가 001~017을 `local`·`remote` 양쪽으로 보고하며,
  016·017은 실제로 `supabase db push`로 적용했다. `schema_migrations`가 정상 채워져 있으므로 CLI 경로가 유효하다.
  (`README.md:25`의 "SQL Editor에서 수동 적용" 안내는 오래된 문서다. 1단계에서 함께 고친다.)
- **워크트리 018을 rename하기 전에 idempotent로 만든다.** `016_admin_user_management.sql`의
  `create table`(:31)·`create index`(:43)·`create policy`(:48)에 `if not exists` / `drop ... if exists`를 넣는다.
  다른 환경에서 016으로 이미 적용된 적이 있으면 재실행 시 전체 트랜잭션이 롤백된다.

**시나리오 2: 0원 주문이 제약에 걸려 베타 주문 생성이 실패한다.**
- 징후: `create_admin_beta_ai_order`가 check 위반으로 롤백. 또는 `payment_id` NOT NULL 위반.
- 원인: **제약이 둘이다.** `001:146` `amount_krw > 0`(인라인 무명)과 `011:7-8` `orders_amount_tax_check`(명시적).
  rev1은 후자만 봤다. 여기에 `001:145` `payment_id not null unique`까지 세 가지를 모두 만족해야 한다.
- 대응: 019에서 **두 제약을 각각 다른 방법으로** 교체한다.
  `011:7`은 이름이 있으므로 `drop constraint if exists`, `001:146`은 무명이므로 `pg_constraint` 조회(016 방식).
  `payment_id`는 `'beta-' || gen_random_uuid()`로 채운다 — 주문 id를 재사용하지 않는다(3.6 참조).

**시나리오 3: 관리자 계정이 진단을 완료하지 않아 베타 주문이 만들어지지 않는다.**
- 징후: 주문 생성은 되는데 `readiness` 스냅샷이 비고, 보고서가 유사사례 가정으로만 채워진다.
- 원인: AI 주문 경로는 조직의 최근 assessment를 읽는다. 관리자 조직에 진단 이력이 없을 수 있다.
- 대응: **코드를 바꾸지 않는다.** `route.ts:79-95`는 `maybeSingle()`로 진단 없음을 허용하며,
  이는 유료 고객에게도 동일하다. 베타만 거절하면 원칙 1(같은 코드 경로)을 깨고,
  전체를 거절하면 기존 유료 고객의 회귀가 된다.
  → **3단계 rollout 체크리스트 항목**으로만 둔다: 두 계정이 베타 실행 전에 준비도 진단을 완료한다.

### 1.2 워크트리 상태

- HEAD가 `cf30037`로 main(`e1ef75c`)보다 **14커밋 뒤처짐**
- 미커밋 변경 19건

## 2. 실행 순서 — 3단계 배포

각 단계는 독립적으로 배포·검증 가능하며, 앞 단계가 끝나야 다음이 시작된다.

### 1단계 — 워크트리 통합 (베타 기능 없음)

목표: admin user management를 main에 올리고 `kyeon@tansley.kr`을 관리자로 승격한다.

1. 워크트리를 main에 **rebase**한다. 충돌은 `app/globals.css` 하나뿐이며, 양쪽 모두 파일 끝에
   규칙을 덧붙이는 성격이라 두 블록을 모두 살린다.
2. **rename 전에 idempotent로 만든다** — `create table`(:31)·`create index`(:43)·`create policy`(:48)에
   `if not exists` / `drop policy if exists`를 넣는다.
3. `016_admin_user_management.sql` → **`018_admin_user_management.sql`**로 rename.
   테스트 파일(`016_admin_user_management.test.ts:4`가 파일명을 `readFileSync`로 참조)도 함께 고친다.
4. `README.md:25`의 "SQL Editor에서 수동 적용" 안내를 실제 절차(`supabase db push`)로 고친다.
5. `supabase migration list`로 018이 `local`에만 있고 `remote`가 비어 있음을 확인한다.
6. `npm test` · `npx tsc --noEmit` · `npm run build` 통과 확인.
7. 커밋 → 배포 → `supabase db push` → `admin_role_audit_log` 테이블 존재를 직접 확인한다.
8. 관리자 화면에서 `kyeon@tansley.kr`을 `admin`으로 승격한다.
9. 두 계정의 auth UUID를 **읽기 전용으로** 확인해 기록한다.
10. **두 계정의 `organization_id` · `job_title` · `phone_enc`를 조회한다.** 셋 다 주문 생성의 전제다.
    - `organization_id`가 null이면 주문 자체가 불가하다(`001:139`). 조직을 만들지, 기존 조직에 넣을지 정한다.
      **기존 고객 조직에 넣으면 안 된다** — `app/admin/page.tsx:57`이 `organization_id`로 회사 행을 묶어
      베타 주문이 그 고객의 주문 목록에 섞이고, `route.ts:81`이 그 조직의 진단을 읽는다.
      → **관리자 전용 조직을 따로 만든다.**
    - `job_title`·`phone_enc`가 비면 `:71-76`에서 403이 난다. **베타를 예외로 두지 말고 두 필드를 채운다**
      (예외를 두면 원칙 1의 "같은 코드 경로"가 깨진다).

**이 단계는 베타 기능을 포함하지 않는다.** 통합 실패와 기능 실패를 분리하기 위해서다.

### 2단계 — 베타 기능 구현 (플래그 OFF로 배포)

목표: 코드와 스키마를 올리되 아무도 쓸 수 없는 상태로 둔다.

1. `lib/admin-ai-beta.ts` — 환경변수 파서와 자격 판정. **테스트 먼저.**
2. `019_admin_ai_expert_beta_access.sql` — `billing_mode` 컬럼, 금액 제약 교체, 원자 생성 RPC.
3. `/api/orders` 베타 분기. 정상 결제 회귀 테스트 통과 확인.
4. `CheckoutButton`이 `requiresPayment === false`를 처리.
5. 주문 상세·환불·webhook 경계.
6. 비용 계산과 관리자 지표 분리.
7. 커밋 → 배포 → `supabase db push`. **환경변수는 아직 설정하지 않는다.**

플래그가 없으므로 이 시점에는 유료 경로만 동작한다. 회귀가 없는지 여기서 확인한다.

### 3단계 — 베타 개시

1. Vercel에 `ADMIN_AI_BETA_ACCESS_ENABLED=true`와 두 UUID 설정.
2. 두 계정으로 준비도 진단을 먼저 완료한다(시나리오 3).
3. 계정별 smoke test: 상세 → 0원 확인 → 동의 → 결제창 없이 주문 상세 → 입력·파일·추가질문 → 실제 모델 실행 → 보고서 → 사실 정정.
4. 관리자 화면에서 베타 비용이 매출과 분리되어 집계되는지 확인.

## 3. 설계 (원안 채택, 변경분만 기술)

### 3.1 `billing_mode`

```sql
alter table public.orders add column billing_mode text not null default 'paid';
alter table public.orders add constraint orders_billing_mode_check
  check (billing_mode in ('paid', 'admin_beta'));
```

`admin_beta` 주문은 실행 권한 상태로 기존 `paid`를 재사용한다. 화면에는 원시 상태를 노출하지 않는다.

### 3.2 금액 제약 교체 (019)

> ⚠️ **016의 `pg_constraint` 조회 패턴을 여기에 그대로 쓰면 안 된다.**
> `orders`에는 `amount_krw`를 포함하는 check가 **셋**이다 — `001:146`(대상),
> `001:148` `provider_amount_krw >= 0`, `001:156` `platform_fee + provider_amount = amount`.
> 016의 `limit 1`은 `order by`가 없어 어느 것이 잡힐지 비결정적이고,
> `if constraint_name is not null` 때문에 **틀린 것을 지워도 조용히 성공한다.**
> 최악의 경우 결제 테이블의 정산 항등식(`001:156`)이 사라지고, 정산 불일치가 날 때까지 아무도 모른다.

Postgres는 단일 컬럼 인라인 check에 `<테이블>_<컬럼>_check` 이름을 자동 부여하므로
**결정적인 이름으로 드롭하고, 남아 있으면 마이그레이션을 실패시킨다.**

```sql
-- 1) 0원을 막는 두 제약 제거 (이름이 결정적이다)
alter table public.orders drop constraint if exists orders_amount_krw_check;
alter table public.orders drop constraint if exists orders_amount_tax_check;

-- 2) 의도한 제약이 실제로 사라졌는지 확인. 남아 있으면 019 전체를 롤백한다.
do $$
begin
  if exists (
    select 1 from pg_constraint
    where conrelid = 'public.orders'::regclass and contype = 'c'
      and pg_get_constraintdef(oid) ilike '%amount_krw > 0%'
  ) then
    raise exception 'orders.amount_krw > 0 제약이 남아 있어 019를 중단합니다';
  end if;
end $$;

-- 3) billing_mode 조건부로 재생성. 이름을 명시한다.
alter table public.orders add constraint orders_amount_by_billing_mode_check check (
  (billing_mode = 'paid'
     and amount_krw > 0 and supply_amount_krw > 0 and vat_amount_krw >= 0
     and supply_amount_krw + vat_amount_krw = amount_krw)
  or
  (billing_mode = 'admin_beta'
     and amount_krw = 0 and supply_amount_krw = 0 and vat_amount_krw = 0
     and platform_fee_krw = 0 and provider_amount_krw = 0)
);
```

`001:156`(`platform_fee + provider_amount = amount`)은 **건드리지 않는다.** 0+0=0으로 통과한다.

**019가 추가하는 모든 제약에 이름을 붙인다.** 무명으로 두면 지금 겪는 문제를 그대로 반복한다.

| 모드 | `supply_amount_krw` | `vat_amount_krw` | `amount_krw` | `platform_fee_krw` | `provider_amount_krw` |
|---|---:|---:|---:|---:|---:|
| `paid` | > 0 | ≥ 0 | 공급가 + 부가세 | 기존 계산 | 기존 계산 |
| `admin_beta` | = 0 | = 0 | = 0 | = 0 | = 0 |

### 3.3 원자 생성 RPC

`create_admin_beta_ai_order`가 한 트랜잭션에서 주문과 `ai_agent_runs`를 만든다.
호출자의 활성 `admin` 역할을 RPC 안에서 **다시** 검증한다.

**스냅샷은 PL/pgSQL에서 다시 만들지 않는다.** `service_snapshot`·`terms_snapshot`은
`route.ts:114-141`이 유료 주문과 **똑같이** 만들어 `jsonb` 인자로 넘긴다. RPC의 역할은
원자적 insert와 역할 재검증뿐이다. 계약 모양을 두 언어에 이중으로 두면 반드시 어긋나고,
`paidServiceSchema`(`ai-agent-runs route:132`)가 검증하는 대상이 갈라진다.

`service_snapshot`에 실제 상품가를 `listPriceKrw`로 보존하고,
`terms_snapshot`에 `paymentRequired: false`, `refundEligible: false`를 기록한다.

run 상태는 **`'intake'`**다. 원안의 `awaiting_intake`는 `010:22-24`에 없는 값이라 insert가 실패한다.

**호출자 식별**: 서비스 롤 클라이언트로 호출하므로 RPC 안에서 `auth.uid()`는 **null**이다.
따라서 `p_buyer_id uuid`를 인자로 받아 그 id의 `profiles.role = 'admin' and deleted_at is null`을 검증한다.
워크트리의 `manage_user_role`(`016:54`)은 `auth.uid()`를 쓰지만 그것은 `authenticated` 호출용이라
여기 선례가 되지 않는다.

**grant는 반드시 건다.** PostgREST는 `public` 스키마 함수를 `authenticated`에 자동 노출하므로,
revoke하지 않으면 로그인한 아무나 임의의 `service_snapshot`·`product_key`로 주문을 찍을 수 있다.
기존 RPC(`010:286-295`, `013:82-83`)와 같은 형태로 건다.

```sql
revoke all on function public.create_admin_beta_ai_order(...) from public, anon, authenticated;
grant execute on function public.create_admin_beta_ai_order(...) to service_role;
```

> 다만 이 grant가 **서비스 키 유출을 막지는 못한다.** `createSupabaseAdminClient()`가 이미
> 서비스 키로 `orders`에 직접 insert한다(`route.ts:100`). RPC 안의 역할 재검증은
> **이 라우트의 버그**를 막는 장치다. 둘 다 필요하며 서로를 대체하지 않는다.

### 3.4 권한 판정 (fail closed)

```text
ADMIN_AI_BETA_ACCESS_ENABLED=true
ADMIN_AI_BETA_USER_IDS=<uuid-1>,<uuid-2>
```

플래그 정확히 `true` · UUID 정확히 2개 · 서로 다름 · 형식 유효 · 현재 사용자가 목록에 있음 ·
프로필이 `deleted_at is null`이고 `role = 'admin'`. 하나라도 어긋나면 유료 경로만 남는다.

이메일을 코드·DB·클라이언트 어디에도 하드코딩하지 않는다. UUID 목록은 클라이언트로 보내지 않는다.

### 3.5 역할 게이트 완화 — AI 경로에만 좁게 연다

`app/api/orders/route.ts:65`는 **AI 분기(`:78`)와 사람 분기(`:153`)를 모두 덮는다.**
여기에 `|| isBetaEligible`을 그대로 넣으면, 베타 관리자가 provider `serviceId`를 보내
**정가 사람 주문을 만들 수 있고** 결제 시 정산 의무까지 생긴다(`webhook:102`).

따라서 조건을 **AI 상품일 때만**으로 좁힌다.

```ts
// aiCatalogService는 :36에서 이미 계산된다
const betaEligible = Boolean(aiCatalogService) && await isAdminBetaEligible(user.id);
if (!profile?.organization_id || (profile.role !== "startup" && !betaEligible)) { ... 403 }
```

함께 확인할 것:
- `orders.organization_id`는 `not null`(`001:139`)이다. 관리자 계정에 조직이 없으면 여전히 막힌다.
- `:71-76`이 `job_title`·`phone_enc`를 요구한다. 관리자 계정은 비어 있을 가능성이 높으므로
  **베타를 예외로 두거나 두 필드를 먼저 채운다.** 그렇지 않으면 역할 실패와 구분되지 않는 403이 난다.

### 3.5.1 베타 응답 계약

`components/checkout-button.tsx:74`가 `order.paymentId`를 필수로 읽으므로 응답 모양을 명시한다.

```jsonc
// 정상 결제
{ "orderId": "uuid", "paymentId": "gtm-uuid", "amount": 218900, "requiresPayment": true }
// 관리자 베타 — paymentId를 클라이언트에 주지 않는다
{ "orderId": "uuid", "amount": 0, "requiresPayment": false }
```

`CheckoutButton`은 `requiresPayment === false`이면 `paymentId`를 읽기 전에 `/orders/{orderId}`로 이동한다.
DB의 `payment_id`(3.6)는 서버에만 존재한다.

### 3.6 `payment_id` — 주문 id를 재사용하지 않는다

`001:145`가 `payment_id text not null unique`라 베타 주문도 값이 필요하다.
**`'beta-' || gen_random_uuid()`를 쓴다.**

`gtm-<order-id>` 형식을 재사용하면 안 된다. `webhook:57`이 **`payment_id`로 주문을 찾기 때문에**,
베타 주문 id를 알아낸 사람이 `gtm-<beta-order-id>`로 100원을 결제하면 webhook이 그 베타 주문을 찾아
금액 불일치(`010:94`)로 **`disputed`로 만들어 버린다.** 그러면 `013:56`이 `paid|completed`만 허용하므로
해당 베타 주문은 영구히 실행 불가가 되고 관리자 화면의 분쟁 목록도 오염된다.

### 3.7 중복 생성 제한과 취소 경로

주문 생성에는 idempotency key가 없고(`route.ts:96`이 매번 새 UUID), 유료 경로에서는 가격이
사실상 유일한 제동 장치였다. 무료가 되면 그 제동이 사라진다.

```sql
create unique index orders_admin_beta_open_run
  on public.orders(buyer_id, product_key)
  where billing_mode = 'admin_beta' and status in ('paid', 'service_started');
```

관리자 1인당 상품 1개당 **진행 중 베타 주문 하나**로 제한되어 더블클릭 중복 생성을 막는다.

> ⚠️ **인덱스만 두면 관리자가 그 상품에서 영구히 잠긴다.**
> 실제 상태 흐름은 이렇다 — 생성 시 `paid` → 예약 시 `service_started`(`013:60-62`) →
> 성공하면 `completed`, **실패하면 다시 `paid`**(`010:280`). 그리고 `013:53`이
> `generation_count >= 2`면 예약을 거절한다.
> 즉 **두 번 실패하면 주문이 `paid`에 머문 채 영원히 진행되지 않고**, 인덱스 술어
> `status in ('paid','service_started')`에 계속 걸려 새 베타 주문을 만들 수 없다.
> 게다가 이 계획은 베타의 환불·취소 경로를 막아 두어 빠져나갈 길이 없다.
> 중단하고 다시 하는 것이 베타 테스트의 본질인데, 그걸 막는 설계다.

**따라서 취소 경로를 반드시 함께 연다.** `refund/route.ts`의 주문 로드 직후(`:23` 다음),
`:24`의 검토 분기보다 먼저 베타 전용 분기를 둔다.

```ts
if (order.billing_mode === "admin_beta") {
  // 결제가 없으므로 게이트웨이를 부르지 않는다. 상태만 정리해 슬롯을 푼다.
  await admin.from("orders").update({ status: "cancelled" }).eq("id", id).eq("buyer_id", user.id);
  return NextResponse.json({ status: "cancelled" });
}
```

`cancelled`는 인덱스 술어 밖이라 슬롯이 풀리고, 관리자가 같은 상품을 다시 시험할 수 있다.

또한 베타가 사람 주문 형태를 갖지 못하도록 못 박는다(**이름 명시**).

```sql
alter table public.orders add constraint orders_beta_is_ai_only_check
  check (billing_mode = 'paid' or order_kind = 'ai_agent');
```

## 5. 검증 계획

### 5.1 단위

- UUID 파서: 0·1·3개, 중복, 형식 오류, 공백 → 전부 false
- 자격 판정: 플래그 ON + 허용 UUID + 활성 admin만 true. 탈퇴 admin·startup·제3 admin·플래그 OFF는 false
- 비용: 유료는 결제수수료 3.3% 유지, 베타는 0. 모델·도구·지원비는 양쪽 동일
- 지표: 베타가 매출·전환·미시작 목록에서 제외되고 베타 비용 합계에는 포함

### 5.2 API

- 허용 두 관리자 각각 베타 주문 생성 성공
- 제3 관리자·startup·provider는 베타 분기 진입 불가
- 클라이언트가 `billingMode`·무료 필드를 보내도 무시
- 플래그 OFF에서 기존 유료 응답 유지
- 환불 API가 베타 주문에서 **어떤 상태 변경보다 먼저** 종료(`:24` 검토 분기, `:49` `disputed` 전환 이전)
- webhook이 베타 주문 상태를 변경하지 않음
- **베타 자격 관리자가 provider `serviceId`를 보내면 403** (사람 주문 경로가 열리지 않음)
- 같은 관리자·같은 상품으로 두 번 요청하면 두 번째가 거절됨

### 5.3 DB

- RPC가 주문과 run을 원자 생성. run insert 실패 시 주문도 롤백
- `paid` 모드는 0원 불가, `admin_beta`는 모든 금융 필드가 정확히 0
- 베타도 reserve → complete/fail 전이와 토큰·비용 저장이 정상
- 베타에는 payment event와 settlement가 생성되지 않음
- `admin_beta`에 `provider_id`를 넣으면 check 위반 (사람 주문 형태 불가)
- `payment_id`가 `beta-` 네임스페이스이고 `gtm-`과 충돌하지 않음
- **비용 회귀**: `grossAmountKrw = 0`이면 `paymentFeeKrw = 0`이고 모델·도구·지원비는 그대로 기록됨
- **018이 remote에 없음을 확인한 뒤 push했는지** (1단계 게이트)

### 5.4 E2E

두 계정 각각: 상세 진입 → 0원·안내 확인 → 동의 → 결제창 없이 주문 상세 →
준비도 스냅샷 → 입력·모름·파일·추가질문 → 실제 모델·웹 조사 → 보고서 출처·가정·문항 추적 →
사실 정정 1회 → 재접속 후 결과 유지 → 관리자 화면에서 비용·상태 확인.

대조군: 제3 관리자·일반 계정은 베타 UI를 보지 못한다. 일반 창업자 결제는 PortOne 경로 유지.
320px에서 overflow·focus·상태 문구 확인.

> **이 저장소의 검증 수단을 정확히 적는다.**
> - §5.3의 "DB 테스트"는 실제 DB에 붙지 않는다. 기존 마이그레이션 테스트는
>   `readFileSync` + `toContain` **문자열 단언**이다(`016_admin_user_management.test.ts:9-16`).
>   따라서 "롤백된다", "전이가 동작한다" 같은 **동작 주장은 문자열로 검증할 수 없다.**
>   → SQL 문자열 단언으로 가능한 것과, 브랜치 DB에서 psql로 직접 확인할 것을 나눠 적는다.
> - §5.4는 **수동 스모크 스크립트**다. Playwright도 e2e 설정도 없고 `npm test`는 vitest뿐이다.

### 5.5 실행 시점 권한 — 의도적으로 fail open

자격 검증은 **주문 생성 시점에만** 한다. 실행 경로(`ai-agent-runs route:108-116`)는
`buyer_id`만 확인하고 역할을 다시 보지 않으며, `reserve_ai_agent_generation`(`013:34-79`)에도
역할 검사가 없다.

따라서 **관리자가 강등되거나 allowlist에서 빠져도 이미 만든 베타 주문은 계속 실행할 수 있다.**
이는 수용 기준 7("기존 베타 주문은 계속 열고 완료할 수 있다")과 같은 성질이며, 둘을 동시에 가질 수 없다.

**입장: fail open을 택하고 명시한다.** 근거는 두 가지다.
- `buyer_id` 필터(`ai-agent-runs route:113`)가 소유자 본인으로 제한한다.
- 생성 중인 보고서를 권한 변경으로 잃게 하는 것이 더 나쁜 결과다.

원칙 3(fail closed)은 **신규 생성에만** 적용된다고 문서에 못 박는다.

> 3.7의 인덱스는 **동시성**만 제한하지 지출을 제한하지 않는다. `013:56`이 `completed` 주문의
> 재예약을 허용하고 `013:53`이 건당 2회를 허용하므로, 완료된 주문은 인덱스 술어 밖에서
> 한 번 더 실행될 수 있고 새 주문도 얼마든지 만들 수 있다. 지출 상한은 8장의 미결로 남는다.

### 5.6 실패 사유 구분

UUID 오타·플래그 OFF·비관리자·AI 서비스 자체가 꺼진 경우가 모두 `route.ts:67`의 같은 403 문구로 나온다.
운영자가 원인을 알 수 없으므로 **서버 로그에만** 구분자를 남긴다:
`flag_off` / `not_in_allowlist` / `not_admin` / `ai_services_off` / `not_ai_product`.
allowlist 자체는 절대 로그에 남기지 않는다.

`ai_services_off`가 필요한 이유: 3.5의 조건이 `aiCatalogService`에 의존하는데,
이 값은 `aiExpertServicesEnabled()`가 꺼지면 null이 된다(`route.ts:36`). **네 번째 환경변수 의존이다.**

### 5.8 관측 (Observability)

인증·결제·프로덕션 마이그레이션을 건드리므로 로그만으로는 부족하다.

| 항목 | 내용 |
|---|---|
| 생성 로그 | 베타 주문 생성 시 구조화 로그 1줄 — `order_id`, `product_key`, 결과. **UUID·allowlist는 남기지 않는다** |
| 지출 집계 | `billing_mode = 'admin_beta'` 주문의 `estimated_total_variable_cost_krw` 누적 합계를 관리자 화면에 노출 |
| 지출 경보 | 누적 베타 비용이 임계치를 넘으면 알림. 5.5에서 지출이 상한 없이 열려 있으므로 이것이 유일한 제동이다 |
| 거절 로그 | RPC 역할 재검증 실패 시 로그. 자격 판정 실패는 5.6의 구분자를 남긴다 |

### 5.7 수용 기준

1. 정확히 두 UUID 계정만 결제 없이 새 주문을 만들 수 있다.
2. 두 계정이 활성 `admin`이 아니면 **새 베타 주문 생성**이 불가하다.
   (실행 시점 권한은 5.5대로 **의도적으로 fail open**이며, 이 기준은 생성에만 적용된다.)
3. 결제창과 PortOne API가 베타 흐름에서 호출되지 않는다.
4. 베타 주문의 모든 금융 필드가 0이고 매출·정산·환불 지표에 들어가지 않는다.
5. 모델·웹 조사·파일·추가질문·보고서·정정·출처 검증이 유료와 동일하다.
6. 실제 비용이 기록되고 관리자 화면에서 별도로 확인된다.
7. 플래그 OFF 시 신규 베타 주문만 중단되고 기존 베타 주문은 계속 열고 완료할 수 있다.
8. 관리자 UUID·allowlist가 클라이언트 응답과 UI에 노출되지 않는다.
9. `supabase migration list`에서 018·019가 local·remote 양쪽에 정확히 한 번씩만 나타나고,
   `admin_role_audit_log` 테이블이 실제로 존재한다.
10. 베타 자격 관리자가 provider `serviceId`로 주문을 시도하면 **403**이다(사람 주문 경로 차단).
11. 같은 관리자가 같은 상품으로 진행 중 베타 주문을 두 개 만들 수 없다(부분 유니크 인덱스).
12. 베타 주문의 `payment_id`가 `beta-`로 시작하고 `gtm-` 네임스페이스와 겹치지 않는다.
13. 전체 테스트·typecheck·build 통과.

## 6. 롤백

1. `ADMIN_AI_BETA_ACCESS_ENABLED=false` → 신규 베타 주문 즉시 중단. 유료 경로 무영향.
2. 기존 베타 주문은 읽기·실행을 계속 허용해 작업 손실을 막는다.
3. 컬럼·제약을 즉시 제거하지 않는다. `billing_mode`는 기본값 `paid`라 존재 자체로 부작용이 없다.
4. 1단계(018)는 되돌리지 않는다. 관리자 관리 기능은 베타와 독립적으로 유효하다.
5. **019가 엉뚱한 제약을 지운 경우**: 3.2의 `raise exception` 가드가 019 전체를 롤백하므로
   프로덕션에는 반영되지 않는다. 그래도 반영되었다면 `pg_constraint`에서 현재 제약 집합을 덤프해
   `001:146`·`001:156`·`011:7-8`과 대조하고, 누락분을 원문 그대로 재생성한다.
6. **베타 주문이 잠긴 경우**(2회 실패 후 `paid` 고착): 3.7의 취소 분기로 `cancelled` 처리해 슬롯을 푼다.
   취소 분기가 아직 없으면 `update orders set status='cancelled' where id=... and billing_mode='admin_beta'`.

## 7. ADR

**결정**: `orders.billing_mode = paid | admin_beta`를 도입하고 실행 상태는 기존 `paid`를 재사용한다.
워크트리 통합 → 기능 배포(플래그 OFF) → 베타 개시의 3단계로 나누고, 마이그레이션을 018·019로 다시 매긴다.

**동인**: 마이그레이션 번호가 이미 프로덕션에 소진됨. 워크트리가 14커밋 뒤처짐(겹치는 파일은 CSS 하나).
0원 주문을 막는 제약이 둘이고 `payment_id`가 필수.

**대안**: 워크트리에서 한 번에 완성(016 충돌 미해결로 기각), 쿠폰 발행(비범위·지표 오염으로 기각),
수동 INSERT(같은 코드 경로가 아니라 기각), 새 `access_granted` 상태(원안에서 이미 기각 — 상태 전이·UI·RPC·테스트가 전면 분기).

**결과**: 배포가 세 번으로 늘어난다. 대신 통합 실패와 기능 실패가 분리되고, 각 단계에서 되돌릴 지점이 명확하다.
실행 시점 권한은 **의도적으로 fail open**이며(5.5), 노출 범위는 3.7의 부분 유니크 인덱스로 묶는다.

**후속**: 무료 체험·쿠폰·파트너 크레딧처럼 결제 외 entitlement가 세 종류 이상 생기면
`billing_mode` 확장이 아니라 별도 entitlement 모델을 검토한다.

## 8. 미결 사항

1. **워크트리 rebase 주체** — 충돌은 `app/globals.css` 하나뿐이라 규모는 작다. 내가 할지 워크트리 작업자가 할지만 정하면 된다.
2. **관리자 조직의 준비도 진단** — 베타 실행 전 두 계정이 진단을 완료해야 한다. 실제 데이터로 할지 테스트 데이터로 할지.
3. ~~관리자 계정의 `job_title`·`phone_enc`~~ — **결정됨**: 예외를 두지 않고 두 필드를 채운다(1단계 10).
4. ~~`organization_id`~~ — **결정됨**: 관리자 전용 조직을 따로 만든다(1단계 10).

5. **베타 지출 상한** — 3.7의 인덱스는 동시성만 묶고 지출은 묶지 않는다(5.5 참조).
   RPC에 계정별 누적 베타 주문 수 상한을 둘지, 아니면 상한 없이 5.8의 모니터링으로만 관리할지 결정이 필요하다.
