# 구현 계획 — 상품별 AI 모델 라우팅

승인 설계: [docs/design/2026-08-19-상품별-AI-모델-라우팅.md](../design/2026-08-19-상품별-AI-모델-라우팅.md) + 확정 UI 샘플(공통 기본값 3단계를 3열 한 줄, 아래 상품별 조정 표, 배너·사유·버튼 같은 폭). 브랜치 `feat/product-model-routing`, 태스크 단위 커밋, 완료 후 main 머지·배포. **DB push는 실행 직전 사용자 확인.**

## Goal
공통 기본값 + 상품별 오버라이드를 한 버전으로 관리하고, 실행 스냅샷은 지금 모양(`{stage:{model,effort}}`) 그대로 유지한다. 첫 배포는 동작 변화 0(패키지 `high`는 코드 → 오버라이드 시드).

## 전역 제약
- 스냅샷·어댑터·진행 화면·검증 코드는 손대지 않는다.
- 폴백 없음. 오버라이드도 카탈로그 안 모델·지원 노력·키 있는 제공자만.
- 오버라이드 키는 화면에 보이는 AI 상품(`listCatalogProducts()`에서 `includedAgentIds.length > 0`)만 허용.

## 태스크

### T1 `lib/ai-models/routing.ts` — 순수 로직 (TDD)
- `productOverridesSchema`: `z.record(z.string(), routesSchema.partial().strict())` (단계별 완전한 route만; 빈 객체 허용).
- `validateStageRoute(stage, route, env)` 로 기존 검사 분리 → `validateRoutes`가 재사용.
- `validateProductOverrides(input, env, allowedProductIds)`: `{ok, overrides}` | `{ok:false, error: RoutesValidationError | "unknown_product"}`.
- `effectiveRoutes(defaults, overrides, productId)`: 단계 단위 얕은 병합(DB `||`와 동일 의미). 테스트로 DB 병합과 같은 결과임을 잠근다.
- `diffRouting({routes, overrides}, {routes, overrides})`: 공통 diff + `productChanges[{productId, stage, from|null, to|null}]`.
- `describeRouting(routes, overrides, locale)`: 기존 문구 + ` · 상품 조정 N건`.
- 테스트 `routing.test.ts` 확장: 스키마, unknown_product, effective merge, diff(추가/삭제/변경), describe.

### T2 마이그레이션 `supabase/migrations/025_product_model_routing.sql`
- `alter table ai_model_routing_configs add column product_overrides jsonb not null default '{}'::jsonb;`
- `alter table ai_agent_runs add column model_route_version integer;`
- `reserve_ai_agent_generation` 재정의(024 본문 기준): `select routes, product_overrides, version into r, o, v …`; `effective := r || coalesce(o -> locked_order.product_key, '{}'::jsonb)`; `model_route_snapshot = effective, model_route_version = v`.
- `drop function if exists public.apply_ai_model_routing(jsonb, text, uuid);` → `apply_ai_model_routing(p_routes jsonb, p_product_overrides jsonb, p_reason text, p_actor uuid)`; 오버라이드는 `jsonb_typeof = 'object'`만 확인(모양 검증은 서버 액션).
- 시드: 활성 행의 `product_overrides`에 `pkg-feasibility`·`pkg-entry-design` = `{public_research: routes->'public_research' || '{"effort":"high"}', final_report: routes->'final_report' || '{"effort":"high"}'}` (모델은 현재 기본값 유지).
- 권한: reserve → service_role, apply → service_role (022와 동일).

### T7 검증·배포
- `npx tsc`, `npx vitest run`, `npm run build`.
- 커밋 순서 T1→T6, main 머지, push, 별칭 → 커밋 확인.
- **DB push(025)는 사용자 확인 후** `supabase db push`. 순서: DB 먼저(새 컬럼·RPC는 옛 코드와 호환: 옛 코드는 3인자 apply RPC를 부르는데 drop되므로 → 코드 배포와 DB push는 같은 시점에. 안전 순서: 코드 배포(새 apply 4인자 호출은 RPC 없어 실패 가능) vs DB 먼저(옛 코드의 3인자 호출 실패). 둘 다 관리자 저장 액션에만 영향 → **DB push 직후 바로 코드 배포**(수 분 창), 그 사이 관리자 저장만 실패. 실행 예약(reserve)은 어느 순서든 동작.
- 배포 후 확인: 새 실행 `model_route_version = 17`, 패키지 주문 스냅샷에 `high`.
