# 상품별 AI 모델 라우팅 — 제안 (pending approval)

작성 2026-08-19. 상태: **제안, 승인 대기**. 코드 변경 없음.

## 왜

"AI 전문가"의 능력은 곧 뒤에 있는 AI의 능력이다. 지금 라우팅은 **전 상품 공통 3단계 하나**(v17: Luna·Luna·Fable 5)이고, 패키지만 코드에 `high`가 박혀 있다(`app/api/ai-agent-runs/[orderId]/route.ts:358`). 그러나 9종 상품은 요구하는 능력이 다르다:

| 상품 | 성격 | 병목이 되는 능력 |
|---|---|---|
| 심층 시장조사 `ai-market-intelligence` | 숫자·산식(TAM/SAM/SOM), 교차검증 | 수치 추론·일관성 → **보고서 모델** |
| 규제·진입요건 `ai-entry-requirements` | 공식 출처 인용, 오류 허용도 최저 | 검색 폭·정확도 → **조사 단계 노력**, 출처 검증 |
| 파트너·생태계 `ai-partner-research` | 다수 실체(기업·URL) 수집, 해석 | 검색 폭 → **조사 모델·노력** |
| 고객 검증·실증 `ai-customer-validation` | 실험 설계, 프레임워크 | 추론 → 보고서 모델 (중간) |
| 현지화 사업모델 `ai-local-bmc` | 프레임워크 적용, 논리 | 추론 → 보고서 모델 (중간) |
| TCE·재무 `ai-tce-finance` | 계산·재무 가정 | 수치 추론 → **보고서 모델** |
| GTM 운영 `ai-gtm-operations` | 실행 계획, 체크리스트 | 추론 (중간) |
| 패키지 사업성 `pkg-feasibility` (3종 묶음) | 위 A그룹 합 | 이미 `high` 고정 |
| 패키지 진입설계 `pkg-entry-design` (4종 묶음) | 위 B그룹 합 | 이미 `high` 고정 |

같은 모델·노력을 모두에 쓰면 어떤 상품은 과투자, 어떤 상품은 과소투자다. 측정도 상품별로 갈라 봐야 한다.

## 원칙

1. **공통 기본값 + 상품별 오버라이드.** 기본값은 지금처럼 3단계 하나. 상품은 필요한 단계만 덮어쓴다. 안 덮어쓴 단계는 기본값을 따른다.
2. **한 버전에 전부 담는다.** 기본값 변경이든 상품 오버라이드 변경이든 새 버전(v18, v19…)이 생기고 사유가 남는다. 롤백은 지금과 같다.
3. **실행 시점 스냅샷은 지금 모양 그대로.** 실행에 고정되는 `model_route_snapshot`은 계속 `{stage:{model,effort}}` — 기본값과 오버라이드를 합친 "그 상품의 유효 라우팅"이다. 어댑터·화면·검증 코드는 손대지 않는다.
4. **폴백 없음** 유지. 상품 오버라이드도 카탈로그 안 모델만, 키 없는 제공자는 거부.
5. **패키지 `high` 하드코딩은 오버라이드로 옮긴다** — 첫 배포는 동작이 바뀌지 않아야 한다.

## 데이터 모델 (마이그레이션 025)

```sql
alter table public.ai_model_routing_configs
  add column product_overrides jsonb not null default '{}'::jsonb;
-- { "<productId>": { "<stage>": {"model": "...", "effort": "..."} } }  — 단계별 완전한 route만, 부분 객체 없음

alter table public.ai_agent_runs
  add column model_route_version integer;   -- 어느 버전이 이 실행을 만들었나 (측정용)
```

`reserve_ai_agent_generation`에서 유효 라우팅 계산 — jsonb `||`는 최상위 키 단위 얕은 병합이라 단계 단위 덮어쓰기에 정확히 맞는다:

```sql
select routes, product_overrides, version into r, o, v from ai_model_routing_configs where status = 'active';
effective := r || coalesce(o -> locked_order.product_key, '{}'::jsonb);
update ai_agent_runs set model_route_snapshot = effective, model_route_version = v, ... ;
```

`apply_ai_model_routing(p_routes, p_reason, p_actor)` → `apply_ai_model_routing(p_routes, p_product_overrides, p_reason, p_actor)`. 옛 3인자 오버로드는 `drop function`으로 제거(022에서 겪은 오버로드 함정).

**시드**: 활성 v17 행의 `product_overrides`에 `pkg-feasibility`·`pkg-entry-design` = `{public_research:{model:<현재 조사 모델>, effort:high}, final_report:{model:<현재 보고서 모델>, effort:high}}`를 넣고, 같은 배포에서 `route.ts:358`의 패키지 승격 코드를 지운다 → 동작 동일.

## 라우트 적용 지점

- `route.ts` `runStage`: 지금처럼 `snapshot[stage]`를 읽는다. 변경은 **패키지 `high` 승격 한 줄 삭제**뿐.
- 서버 검증(`lib/ai-models/routing.ts`): `validateRoutes` 재사용 — 오버라이드는 `Partial<Routes>`이므로 `validateStageRoute(stage, route, env)`로 쪼개고, 오버라이드 키는 **AI 상품 id 목록**(`lib/catalog/products.ts`에서 `includedAgentIds.length > 0`인 것)만 허용.
- `describeRoutes`/`diffRoutes`: 오버라이드 diff도 이력에 나오게 확장 (`상품 · 단계: A → B`).

## 관리자 UI/UX (`/admin/ai-models`)

한 페이지, 두 층:

1. **공통 기본값** — 지금 폼 그대로 (3단계 × 모델·노력).
2. **상품별 조정** — 표: 행 = 9상품(전문가 7 / 패키지 2로 묶음), 열 = 3단계.
   - 셀 기본 상태: `기본값 따름 · GPT-5.6 Luna · 보통` (회색). 클릭 → 그 셀만 모델·노력 드롭다운이 열리고 값이 정해지면 **초록 테두리 + "조정됨"** 배지, 옆에 `기본값으로` 링크.
   - 저장은 페이지 하단 한 번: "변경 N건 · 사유 입력 → 적용" → 새 버전. 변경 요약에 `공통: …`, `심층 시장조사 · 보고서: Opus 5 medium → Fable 5 high` 식으로 나열.
   - 각 상품 행 오른쪽에 **측정 열**: 최근 30일 실행 수 · 성공률 · 평균 완주 시간 · 평균 비용 (`ai_agent_runs` × `orders.product_key`, `model_route_version` 그룹). 지금은 상품별 숫자가 없어서 "이 상품에 이 모델이 맞나"를 감으로 정한다 — 이 표가 그 판단 근거다.
   - 이력: 버전 목록에 오버라이드 변경도 표시, 롤백은 지금처럼 버전 단위.

모바일은 세로 카드(상품 → 3단계). 기존 컴포넌트(`admin-model-routing-form.tsx`) 확장.

## 측정

- 스냅샷·버전·상품이 실행에 남으니 상품별 × 버전별로 **시간·비용·성공률·검증 실패 사유**를 SQL 한 번에 뽑을 수 있다. 관리자 표에 그대로 노출.
- 품질은 자동 지표가 없다 → 우선은 **완주율·검증 실패율·출처 수·모순 기록 수**를 대리 지표로, 최종은 사람이 읽는다(오늘처럼).

## 실험 설계 — 어디부터

지금까지의 실측(모두 medium): Opus 5 보고서 264초/$0.57, Fable 5 보고서 247초/$1.18, 785초 예산.

| 순서 | 상품 | 가설 | 오버라이드 | 판정 기준 |
|---|---|---|---|---|
| 1 | 심층 시장조사 | 수치 추론은 노력이 효과 있다 | 보고서 Fable 5 **high** (같은 주문 재실행으로 medium과 비교) | 시간 < 600초, 교차검증 정합성, 가정의 구체성 |
| 2 | 규제·진입요건 | 실패 원인은 검색 폭 | 조사 Luna **high**(검색 8회 최대 활용) + 보고서 Fable 5 medium | 공식 출처 인용률, 검증 실패율(어제 0d023bcf 실패 이력) |
| 3 | 파트너·생태계 | 수집 폭은 조사 모델에 달렸다 | 조사 **Opus 5** medium(Anthropic 웹검색) vs Luna high | 검증 통과 출처 수, 실체 수, 해석 난이도 피드백 |
| 4 | TCE·재무 | 계산은 Fable | 보고서 Fable 5 high | 산식 오류 0, 가정 명시 |
| 5 | 고객검증·현지화BMC·GTM운영 | 프레임워크형은 Opus 5로 충분 | 보고서 Opus 5 medium (비용 절반) | 완주율·가독성 동등하면 유지 |
| 6 | 패키지 2종 | 묶음은 최고 품질 | 조사 Luna high · 보고서 Fable 5 high | 785초 안 완주 여부가 관문 |

각 실험은 **주문 1건 재실행 = 한 데이터 점**이다. 같은 입력으로 medium/high, Opus/Fable을 나란히 돌려 사람이 읽는다. 관리자 표의 측정 열이 시간·비용을 자동으로 채운다.
